**Kapsam**

Log hacmi/CPU azaltma çalışmasının ikinci adımı. Ölçülen log dağılımında iki kalem toplamın %50,3'ünü oluşturuyordu: `Event received:` (%43,8) ve asterisk-java kütüphanesinin `No event class registered for event type 'dialstatus'` satırı (%6,5). Kök maliyet analizi (jar bytecode'undan doğrulandı, `asterisk-java-2.0.3.gb`): `Event received:` satırının maliyeti log yazımı değil `ManagerEvent.toString()`. Bu metod reflection tabanlı çalışıyor — `ReflectionUtil.getGetters(Class)` her çağrıda cache'siz `new HashMap()` + `Class.getMethods()` dizi kopyası kuruyor (`ReflectionUtil`'in hiç static alanı yok, yani cache yok), method adı başına `substring` + `toLowerCase(Locale.ENGLISH)` yapıyor ve ~40 alan için `Method.invoke()` çağırıyor. Ölçülen hacimde saniyede ~227 kez tekrarlanıyordu. Kritik nüans: Java argümanı çağrıdan önce hesapladığı için seviyeyi DEBUG'a indirmek TEK BAŞINA bu maliyeti kaldırmıyor; `isDebugEnabled()` guard'ı zorunlu.

İkincil risk: `logback.xml` async kuyrukları `discardingThreshold=0` ile kayıpsız modda; kuyruk dolduğunda satır atılmaz, üretici thread bekletilir. Bu satırın üreticisi FIX-GLB90048674 ile eklenen tek thread'li AMI eventWorker'ı olduğundan, disk yavaşlamasında event backlog'u riski vardı.
