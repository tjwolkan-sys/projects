# 24.07.2026

### 2026-07-24 10:48:30 +03:00 | GLB90114534 | log-hotpath-async-throttle-dedup

**Kapsam**

NonTurkcell çökmelerinin (CPU/RAM %100, 2 restart) kök nedeni olarak tespit edilen log darboğazının hafifletilmesi. Üç bağımsız kanıt (çökme anı thread dump'ında 84 thread logback CachingDateFormatter kilidinde bloke; Elastic'te event işleme süresinin 22.07'de 1-3 sn → 229 sn'ye fırlaması; ~yarı yüklü turkcell'in hiç çökmemesi) log yazma yolunu işaret etti. Bu görevde çağrı/koda dokunmadan log altyapısı (logback config) ve hot-path'teki verbose/kendini-besleyen log davranışları düzeltildi. Kullanıcı kararları: catalina.out'a yalnız ERROR; dosya logu async; hot-path INFO temizliği; `ManagerConnectionDecorator` "Event received" (satır 624) tüm-event logu KORUNDU (operatör ELK ihtiyacı, filebeat yalnız `gbpowerdialer.log` okuyor → ayrı dosyaya bölünmedi).

**Değişiklikler**

- `gbpowerdialer/src/main/resources/logback.xml`:
  - CONSOLE appender'a `ThresholdFilter level=ERROR` → catalina.out'a yalnız ERROR (çift-yazım israfı kesildi).
  - FILE ve CONSOLE `AsyncAppender` (`ASYNC_FILE`/`ASYNC_CONSOLE`) arkasına alındı: `neverBlock=true` (çağrı thread'i asla bloklanmaz), `includeCallerData=false`, queueSize 8192/1024. Böylece date-format kilidine yalnız tek worker thread dokunur → kilit çekişmesi logback sürümünden bağımsız biter.
  - FILE `immediateFlush=false` (tamponlu yazım).
- `gbpowerdialer/src/main/java/com/powerdialer/engine/asterisk/ami/ManagerConnectionDecorator.java`:
  - `logEventHandlingTime` içindeki event-başına slow-event WARN'u `maybeWarnSlowEvent(...)` ile throttle'landı (`SLOW_EVENT_WARN_THROTTLE_MS=1000`; `AtomicLong` durum + bastırılan sayacı; test için enjekte edilebilir `slowEventClockMs` seam). Eşik (200ms) değişmedi; log baskısında yangını büyüten kendini-besleyen WARN döngüsü kırıldı.
  - `processEvent`: `startTime` ölçümü "Event received" INFO logundan SONRAYA alındı → süre artık log yazma gecikmesini değil yalnız `dispatchEvent` işini ölçüyor.
  - Event log duplikasyonu giderildi: `handleCallCreation`/`handleCallAnswer`/`handleDialerHangup` INFO loglarından (VarSet/ClientPredictiveAnswer/Hangup) tekrarlanan `+ event` çıkarıldı; `call` bağlamı korundu (tam event zaten satır 624'te loglanıyor).
- `gbpowerdialer/src/main/java/com/powerdialer/engine/predictive/dispatcher/PredictiveEventDispatcher.java`: yayın INFO logu (slf4j) → `debug`.
- `gbpowerdialer/src/main/java/com/powerdialer/redis/CallEventPublisher.java`: "Call event published" INFO logu (slf4j) → `debug`.
- `gbpowerdialer/src/main/java/com/powerdialer/redis/RedisUtil.java`: "[GAMMA-SYNC] Redis Bulk Fetch Time" INFO logu → `isDebugEnabled` guard'lı `debug` (commons-logging; ActionLog yazmıyor).
- `gbpowerdialer/src/main/java/com/powerdialer/engine/LSCEngine.java`: "[LSC-RETRY]" INFO logu kaldırıldı. NOT: bu satır `LOG_MODULE.LSC` argümanı taşıdığı için `LoggerDecorator` üzerinden bir ActionLog DB kaydı da yazıyordu; kaldırma ile o denetim kaydı da düştü (kullanıcı onaylı; gerekirse geri alınır).
- Test (TDD): `gbpowerdialer/src/test/java/tests/ami/ManagerConnectionDecoratorSlowEventWarnThrottleRegressionTest.java` (yeni, 3 test): pencere içinde tek WARN + bastırılan sayımı; pencere dolunca tekrar WARN + "(+N bastırıldı)" iliştirme; eşik altı event'te WARN yok.

**Performans Etkisi**

Doğrudan hot-path (AMI event worker + tüm çağrı thread'leri) log maliyetini düşürür. AsyncAppender + CONSOLE-ERROR ile çağrı thread'lerinin log kilidinde bloklanması ortadan kalkar (asıl çökme mekanizması). Slow-event WARN throttle'ı, yavaşlık anında event-başına WARN üretip async kuyruğunu doldurmasını engeller. Event log dedup'ı ve INFO→debug indirimleri satır/byte hacmini düşürür. "Event received" tüm-event logu korunduğu için ELK görünürlüğü değişmez.
